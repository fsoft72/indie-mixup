# Module Creation Guide

**When to Read This File:** When you need to create a new LiWE3 module, understand the module file structure, or learn about the f2c/hexocode pattern.

**ALWAYS** use `flow2code` to generate hexocode from a `*.json` module every time you add / change a JSON module file.

## Quick Reference

| What                          | Where                  |
| ----------------------------- | ---------------------- |
| Framework modules (read-only) | `/liwe3/modules/`      |
| Your custom modules           | `/app/modules/`        |
| Module JSON definitions       | `/work/modules/*.json` |
| Reference module              | `/liwe3/modules/user/` |

## Module Directory Structure

A module has two main parts: **backend** and **frontend**.

```
my-module/
├── backend/
│   ├── src/
│   │   ├── index.ts          # module_init() - entry point, route registration
│   │   ├── schema.ts         # Drizzle ORM table definitions
│   │   ├── types.ts          # Zod schemas and TypeScript types
│   │   ├── events.ts         # Event name constants
│   │   ├── perms.ts          # Permission definitions
│   │   ├── listeners.ts      # Event listeners (inter-module communication)
│   │   ├── internals.ts      # Internal helpers (seed data, etc.)
│   │   └── methods/
│   │       ├── index.ts      # Re-exports all methods
│   │       ├── utils.ts      # Shared imports for methods
│   │       ├── my-method.ts  # One file per endpoint
│   │       └── ...
│   ├── sql/
│   │   └── my-module.sql     # Raw SQL schema (reference)
│   ├── tests/
│   │   └── ...
│   └── package.json
│
└── frontend/
    ├── src/
    │   ├── components/
    │   │   ├── index.ts      # Re-exports components
    │   │   └── MyWidget.svelte
    │   └── actions.ts        # Frontend API helpers
    └── package.json
```

## The HEXOCODE Pattern (f2c_start / f2c_end)

Files in a LiWE3 module are partially generated by an external tool called **flow2code**. The generated code is called **hexocode**.

**Rule: Write your real code INSIDE `f2c_start` / `f2c_end` comment blocks.**

Everything outside these blocks may be overwritten by flow2code regeneration. Code inside the blocks is preserved.

### Block Names

Each block has a label that identifies its purpose:

```typescript
/*=== f2c_start _module ===*/
// Module-level imports (listeners, internals)
/*=== f2c_end _module ===*/

/*=== f2c_start module_init ===*/
// Code that runs during module initialization
/*=== f2c_end module_init ===*/

/*=== f2c_start user_add_headers ===*/
// Imports specific to a method
/*=== f2c_end user_add_headers ===*/

/*=== f2c_start user_add ===*/
// The actual method implementation
/*=== f2c_end user_add ===*/

/*=== f2c_start __types ===*/
// Custom type imports
/*=== f2c_end __types ===*/

/*=== f2c_start utils ===*/
// Custom utility imports
/*=== f2c_end utils ===*/
```

### Example: index.ts

```typescript
import { LOGGED, type LiWEApp, PUBLIC, permissions_register, routeBody, routeGet } from '@backend/liwe3/core';
import { MY_MODULE_PERM_CREATE } from './perms';
// ... generated imports ...

/*=== f2c_start _module ===*/
import { listeners_init } from './listeners';
import { seed_default_data } from './internals';
/*=== f2c_end _module ===*/

// module_init still receives the shared app: it only registers routes and static data
export const module_init = async ( app : LiWEApp ) => {
	console.log( '=== Module: my-module' );

	/*=== f2c_start module_init ===*/
	listeners_init();
	await seed_default_data( app );
	/*=== f2c_end module_init ===*/

	// Routes are registered outside f2c blocks (generated by flow2code).
	// The second argument is the permission GATE, generated from the endpoint's
	// `permissions` block in the module JSON. It is mandatory. See PERMISSIONS.md.
	app.hono.post( '/api/my-module/create', routeBody( my_method, { perms: [ MY_MODULE_PERM_CREATE ] } ) );

	permissions_register( {
		module: 'my-module',
		perms: MY_MODULE_PERMISSIONS,
	} );
};
```

### Example: methods/my-method.ts

```typescript
import { LiWEApp, type LiWECtx, LiWEResponse, responseError, responseSuccess, z } from './utils';
import { paramsValidation } from '@backend/liwe3/core';

/*=== f2c_start my_method_headers ===*/
import { my_table } from '../schema';
import { MyType } from '../types';
import { MY_PERM_CREATE } from '../perms';
/*=== f2c_end my_method_headers ===*/

// Schema is generated by flow2code - do NOT modify
const MyMethodSchema = z.object( {
	name: z.string(),
	// ...
} );

export type MyMethodParams = z.infer<typeof MyMethodSchema>;

export const my_method = async (
	ctx : LiWECtx,
	params : MyMethodParams,
	sys? : LiWESysParams,
) : Promise<LiWEResponse<MyType>> => {
	const validation = paramsValidation( MyMethodSchema, params );
	if ( !validation.success ) return validation.error;

	/*=== f2c_start my_method ===*/
	// YOUR REAL CODE GOES HERE
	const { name } = validation.data;

	const record = await ctx.app.db.select().from( my_table )
		.where( eq( my_table.name, name ) )
		.get();

	if ( !record ) return responseError( 'Not found', 404 );

	return responseSuccess( record );
	/*=== f2c_end my_method ===*/
};
```

## Step-by-Step: Creating a Module

### 1. Define the Module JSON

Create `/work/modules/my-module.json` (or use the flow2code tool). This defines:

- **Types** - Data structures and database tables
- **Endpoints** - API routes with parameters and permissions
- **Permissions** - Access control definitions

See `/work/modules/user.json` for a complete example.

### 2. Run flow2code

Run flow2code against the JSON definition:

```bash
python3 {flow2code installation path}/flow2code.py \
  work/modules/<module>.json \
  -o app \
  -t liwe3-cloudflare-ng \
  --templates-dir work/templates
```

The tool appends `modules/<mod_name>/backend|frontend` to whatever `-o` you give, so pointing `-o` at `app` lands output directly in `app/modules/<module>/backend` and `app/modules/<module>/frontend`, exactly where custom modules belong per the Quick Reference table above.

**First run: verify the folder name landed correctly before writing any
logic.** `mod_name()` lowercases the JSON `name` but does not split camelCase
(see `MODULE_JSON_REFERENCE.md`'s "name -> folder name gotcha"). Run
`ls app/modules/` right after the first generation; if the folder name is
wrong, `rm -rf app/modules/<wrong-name>`, fix the JSON `name`, regenerate.
Nothing is lost since nothing was hand-written yet.

**Every subsequent run preserves `f2c_start`/`f2c_end` blocks** - re-running
after a JSON fix does not lose logic you already wrote inside those blocks.
Only Zod schemas, JSDoc, and non-f2c scaffolding change. Validate the JSON with
`python3 -c "import json; json.load(open(...))"` before every flow2code run -
a syntax error there produces confusing generator errors.

It generates the complete backend structure:

- `schema.ts` - Drizzle ORM table definitions
- `types.ts` - Zod schemas and TypeScript types
- `events.ts` - Event name constants
- `perms.ts` - Permission definitions
- `methods/*.ts` - One file per endpoint (with `f2c_start`/`f2c_end` blocks for your code)
- `methods/utils.ts` - Shared imports
- `methods/index.ts` - Re-exports
- `index.ts` - `module_init()` with route registration
- `listeners.ts` - Event listener stubs
- `package.json` - Dependencies (no `dev` script: see "Backend Type-Check Watcher")
- `tsconfig.json` - `composite: true` plus a `references` entry to `liwe3/backend/core`
- `sql/*.sql` - Raw SQL schema

### 3. Write Your Business Logic

Open the generated method files and write your implementation inside the `f2c_start` / `f2c_end` blocks:

```typescript
// methods/my-method.ts (generated by flow2code)

export const my_method = async ( app, params, c, sys ) => {
	const validation = paramsValidation( MyMethodSchema, params );
	if ( !validation.success ) return validation.error;

	/*=== f2c_start my_method ===*/
	// YOUR CODE HERE
	const record = await ctx.app.db.select().from( my_table )
		.where( eq( my_table.id, validation.data.id ) )
		.get();

	if ( !record ) return responseError( 'Not found', 404 );
	return responseSuccess( record );
	/*=== f2c_end my_method ===*/
};
```

### 4. Add Event Listeners (optional)

If your module needs to respond to events from other modules, add code inside the `f2c_start` blocks in `listeners.ts`.

## Module Initialization

Modules are loaded by the main app. The app calls `module_init()` for each registered module.

In your app's worker entry point:

```typescript
import { module_init as user_init } from '@backend/modules/user';
import { module_init as my_module_init } from '@app/modules/my-module';

// During app startup:
await user_init( app );
await my_module_init( app );
```

## Inter-Module Communication

Use events to communicate between modules. Never import directly from another module's internals.

```typescript
// Emit an event
import { liwe_event_emit } from '@backend/liwe3/core';

const result = await liwe_event_emit( 'user.call.user.get', { id: userId } );

// Register a listener
import { liwe_event_register } from '@backend/liwe3/core';

liwe_event_register( 'user.call.user.get', async ( app, data ) => {
	// handle the event
} );
```

## Rules Summary

1. **Only modify code inside `f2c_start` / `f2c_end` blocks** - hexocode outside these blocks is regenerated
2. **Always return `responseSuccess()` or `responseError()`** - never throw exceptions
3. **Always scope queries by `domain`** - multi-tenant isolation, **unless** the module is a registry-style module that stores the domain registry itself (e.g. `lc_tenant`) - decide this up front (before generating code) and comment the exception in code at the point it matters, since retrofitting later means touching every method:
   ```ts
   // lc_tenant_aziende is the platform-wide tenant registry itself: it is not
   // scoped by the caller's own domain (there is no "own row" to filter to).
   ```
4. **Use events for inter-module communication** - never import other module internals
5. **One method per file** - keeps methods focused and testable
6. **Zod schemas validate all input** - use `paramsValidation()` helper
7. **NEVER** call a method of another module inside a module method. You can call events.

## Backend Type-Check Watcher (`tsc -b`)

`pnpm dev` runs **one** `tsc -b ../../../tsconfig.backend.json --watch` (owned by
`liwe3/backend/core`) that builds every backend package with a shared compiler.
Do **not** give a backend package its own `"dev": "tsc --watch"`: each one loads
a full TypeScript program (300 to 600 MB) and a dozen of them froze the machine.

The generated `package.json` already has no `dev` script, and the generated
`tsconfig.json` already has `composite: true` and a reference to `core`. The rest
is kept aligned by a script, driven by the modules `app/backend/src/index.ts`
imports from `@backend-modules/<name>`:

```bash
work/scripts/sync_modules.py            # write the changes
work/scripts/sync_modules.py --check    # only report, exit 1 if out of sync
work/scripts/sync_modules.py --prune    # also drop @backend-modules/* deps the app does not import
work/scripts/sync_modules.py --frontend # also sync @frontend-modules/* in app/frontend/package.json
work/scripts/sync_modules.py --verbose  # also list the modules and the packages found
work/scripts/sync_modules.py --filters  # pnpm --filter list used by the root `dev` / `predev`
dprint fmt
```

It updates `app/backend/package.json`, the root `tsconfig.backend.json` (only the
modules the app uses plus their workspace dependencies), and `composite` /
`references` in the `tsconfig.json` of each of those packages. It also warns when
`index.ts` imports a module it never passes to `moduleRegister()`, and when a
package still has its own `tsc --watch`. It does not touch `moduleRegister()`
order, `config.json` or `wrangler.jsonc`. Run it after adding or removing a module
in `index.ts`, then `pnpm install --lockfile-only` if a `package.json` changed.

The root `pnpm dev` / `predev` use `--filters`, so a module is built and watched
only if the app imports it (backend) or lists it in `app/frontend/package.json`
(frontend).

Final check: `cd liwe3/backend/core && pnpm exec tsc -b ../../../tsconfig.backend.json`
must end with no errors.

Only the modules the app imports are built and watched. If you edit a module the
app does not import (for example one used only by the playground), nothing
rebuilds its `dist`: run `pnpm -C liwe3/modules/<name>/backend build` by hand, or
add the module to `index.ts`.

## Wiring the Module Into the Worker

In `app/backend` a module is wired by two things:

1. **`app/backend/src/index.ts`** - import `module_init` (and `module_seed` if
   present) from `@backend-modules/<name>` and call
   `await app.moduleRegister( <name>_init, <name>_seed );` with the other modules.
   Order matters: `system` and `user` first.
2. **`work/scripts/sync_modules.py`** - adds `"@backend-modules/<name>": "workspace:*"`
   to `app/backend/package.json` and updates `tsconfig.backend.json` and the
   `tsconfig.json` references (see the section above).

The real npm package name uses a **hyphen** (`@backend-modules/x`). The app has no
`alias` block in `wrangler.jsonc`: wrangler resolves the import through the
workspace package, so it uses the built `dist/` of the module (kept fresh by
`pnpm dev`). Only `playground/backend` (not part of the workspace) lists every
module in `wrangler.jsonc` -> `alias`, pointing to the module `src/index.ts`; add
the module there too if the playground must use it.

Frontend: add `@frontend-modules/<name>` to `app/frontend/package.json` (or run the
script with `--frontend`).

## Repo-Wide Bootstrap Issues (Check Once Per Fresh Clone)

Not specific to any one module - check for these once per fresh clone /
`pnpm install`, not once per module:

- **Invalid dependency names.** pnpm rejects any `dependencies` key containing
  a `/` beyond the `@scope/name` shape. The correct key for a workspace
  package is its real `name` field (check the package's own `package.json` if
  unsure), e.g. `@backend-modules/user`, not `@backend/modules/user`. A single
  invalid key blocks `pnpm install` for the _entire workspace_.
- **`app_init` import.** Import `app_init` from the package root:
  `import { LiWEApp, app_init } from '@backend/liwe3';` - a deeper subpath
  like `'@backend/liwe3/core/src/app'` fails to resolve under wrangler's
  bundler (the alias only covers the exact `@backend/liwe3/core` specifier).
- **`pnpm approve-builds --all`** is needed once per machine for
  `esbuild`/`sharp`/`workerd` postinstall scripts.
- **`.dev.vars` placeholder secrets are too short.** `.dev.vars.example`'s
  `SITE_SECRET`/`JWT_SECRET` placeholders are under the framework's
  32-character minimum. Use a real 32+ char value in your local `.dev.vars`
  (never commit it).
- **`drizzle-kit push` needs a driver.** `db_push.sh` calls `drizzle-kit push`
  against the local SQLite file, which needs `@libsql/client` (or
  `better-sqlite3`) installed as a devDependency at the workspace root:
  `pnpm add -D -w @libsql/client` once.

## Pushing the Schema to Local D1

**Do not hand-write migration SQL.** `scripts/db_push.sh` auto-discovers every
`@backend-modules/*` / `app/modules/*` dependency in the target worker's
`package.json`, resolves each one's `schema.ts`, and runs `drizzle-kit push`
against the live local `.sqlite` file:

```bash
./scripts/db_push.sh all      # or: ./scripts/db_push.sh <module-name>
```

Prerequisite: `wrangler dev` must have run at least once already so the local
D1 sqlite file exists under `app/backend/.wrangler/state/v3/d1/...`. Re-run
`db_push.sh all` any time a `schema.ts` changes, before starting the dev
server for testing - otherwise the first request touching the DB fails with
`no such table: <x>: SQLITE_ERROR`.

## Running `wrangler dev` Without Leaving Orphans

`wrangler dev` spawns a `pnpm` -> `pnpm` (store link) -> `wrangler.js` ->
`node cli.js` -> `workerd` process chain, and wrangler **auto-restarts**
`workerd` internally on crash:

- A background `&`-launched shell survives naive `pkill -f wrangler`/`pkill -f
  workerd` - the top-level bash wrapper keeps respawning a fresh `workerd` on
  the same port, producing an endless "Address already in use" loop. Kill the
  **whole tree** by PID (`ps -eo pid,ppid,cmd | grep -i wrangler`), or use the
  harness's own background-task mechanism (`run_in_background: true`) instead
  of manual `& disown`.
- The local observability endpoint is the fastest way to see server-side
  errors without fighting log-file redirection races:
  ```bash
  curl -s -X POST http://localhost:8787/cdn-cgi/local/explorer/api/local/observability/query \
    -H 'Content-Type: application/json' \
    -d '{"sql":"SELECT message FROM logs ORDER BY rowid DESC LIMIT 30"}'
  ```

## Committing

One commit per endpoint reads cleanly in `git log`/`git blame`, but shared
scaffolding (schema, types, perms, events, `index.ts`, tests infra, worker
wiring, any bootstrap bugfixes discovered along the way) can't be split
per-endpoint without contortion - bundle all of that into the **first**
endpoint's commit (typically `add`, since nothing else is testable without
it), then one commit per remaining endpoint touching only that endpoint's
method file:

```
lc_tenant: implement /lc_tenant/add endpoint      (+ scaffolding, wiring, bootstrap fixes, tests)
lc_tenant: implement /lc_tenant/list endpoint
lc_tenant: implement /lc_tenant/get endpoint
lc_tenant: implement /lc_tenant/del endpoint
```

Run the full check (`tsc --noEmit`, `vitest run`, `restest ... --dont-stop-on-error`)
**before** the first commit and again after the last - the project's
pre-commit hook runs a formatter on staged files and can reformat code after
you've already run tests once; re-verify tests still pass on the
hook-formatted output before calling the work done.
